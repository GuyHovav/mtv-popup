# Product

<!-- impeccable:product-schema 1 -->

## Platform

web (also distributed as an Android app — a thin Capacitor WebView wrapper around the live deployed site, not a separate native codebase)

## Users
Anyone watching a YouTube music video who wants a nostalgic, "second-screen commentary" layer over it — the same audience the original MTV *Pop-up Video* had. No account or login; a visitor arrives, pastes a link, and watches. The user intends to eventually share or deploy this beyond personal use, so treat future visitors as first-time, unguided strangers rather than only the builder.

## Product Purpose
Recreates MTV's *Pop-up Video* format for arbitrary YouTube videos: paste a link, and AI-generated trivia "balloons" pop up over the video at a steady, near-continuous cadence as it plays — some tied to specific moments in the song, most general trivia about the artist/track/era. Success is a visitor pasting a link and getting a genuinely fun, well-paced trivia experience with no manual curation required.

## Positioning
Unlike the original show (a fixed, human-researched library of videos) or a static trivia wiki, this works on *any* YouTube video on demand — facts are generated fresh per video via an LLM (Gemini), not pre-authored. The mechanism a competitor would have to copy is: parse any YouTube URL → pull real metadata (title/author via oEmbed, duration via the IFrame Player) → generate a paced, schema-constrained set of trivia facts → render them as classic pop-up-style balloons synced to actual playback position (including correct behavior on seek/scrub).

## Operating Context
Single-page flow, no navigation: paste URL → video embeds and plays → balloons appear roughly every ~10.5s (one on screen at a time, ~6.5s visible + a randomized 3–5s gap) → scrubbing the video re-arms skipped-back facts and skips over facts scrubbed past. No accounts, no history, no saved videos — each visit is a fresh, stateless session.

## Capabilities and Constraints
- No YouTube Data API key required — video title/author come from YouTube's public oEmbed endpoint; duration is read client-side from the IFrame Player API once it's ready.
- Backend logic (`server/src/lib/`) is framework-agnostic and has two deployment forms: an Express app (`server/`, local dev only) and Vercel serverless functions (`api/`, production) — both wrap the same `POST /api/facts` logic, so there's no behavioral drift between dev and prod.
- Facts are generated by `gemini-2.5-flash-lite` (primary) with a JSON-schema-constrained response (`{ time_seconds, text }[]`), with `minItems`/`maxItems` set to the target count — prompt instructions alone were unreliable for larger counts. On outright Gemini failure (quota/network/blocked/malformed), falls back to `gpt-4.1-mini` (OpenAI); if that also fails, falls back to a small set of generic hardcoded facts. Only the final hardcoded tier counts as "degraded" to the visitor — a successful OpenAI response is just as tailored as a Gemini one.
- Fact density targets ~1 fact per 10.5s of video (a full display+gap cycle), floor 8 / cap 80 facts per video.
- A deterministic post-process pass detects positional language in fact text ("the opening," "kicks off," "the outro," "that's a wrap," etc.) and reassigns that fact's timestamp into the matching part of the timeline (first/last ~12% of duration) — no LLM reliably keeps its own numbers consistent with what its text claims.
- Known, accepted limitation: "moment-specific" facts (including ones about visual content, e.g. an object appearing on screen) are not verified against the actual video frames — the LLM is working from general knowledge/text only, not watching the video, so a visual claim can occasionally be true but mistimed. Fixing this would require video-understanding input (a heavier, more expensive call) or a 3rd-party visual/caption data source; out of scope for now.
- Both Gemini's and OpenAI's free/trial quotas are easy to exhaust with heavy testing; no paid billing configured on either as of this writing.
- Deployed via GitHub → Vercel (static client + `api/` serverless functions in one project); provider API keys live only in Vercel's Environment Variables (Production + Preview), never committed.
- Android distribution is a signed release APK built by `.github/workflows/android-release.yml` (triggered on version tags) and attached to GitHub Releases — not published to the Play Store. The app is a live-URL WebView wrapper (`client/capacitor.config.json` → `server.url`), so it always reflects the current deploy with no separate native rebuild needed when the web app changes; a real Android build only needs re-cutting when the wrapper shell itself changes.
- No database, no auth, no user accounts — each session is independent and nothing persists.

## Brand Commitments
Working name is "Pop-up Video" (📺 emoji mark) — a direct, affectionate homage to MTV/VH1's actual show of the same name. The user has chosen to keep this name for now, but flagged it as worth reconsidering (a distinct name) before any release wider than personal/portfolio use, given it reuses another brand's actual show title. No other naming, logo, or visual-identity commitments exist yet — the current look (dark gradient background, gradient wordmark, hot-pink/cyan/yellow/purple/lime balloon palette) is an implementation default, not a confirmed brand direction.

## Evidence on Hand
No real user testimonials, case studies, or press. No pre-written trivia content — all facts are generated live per video, per session, with no caching between sessions. Do not fabricate testimonials, usage numbers, or press mentions in any future surface work.

## Product Principles
1. Zero setup for the visitor — no login, no API key entry, no manual curation; paste a link and it works.
2. Match the classic show's pacing, not just its look — near-continuous, one-at-a-time trivia beats a handful of sparse, isolated facts.
3. Prefer a plausible, honest fallback over a broken or empty experience — never let an LLM hiccup surface as a dead end.
4. Ground what can be grounded deterministically (timestamps, positional language, seek behavior) rather than trusting model output where a cheap, reliable check exists.
5. Keep the stack proportionate to a demo-scale project — no database, no auth — until real usage demands otherwise.

## Accessibility & Inclusion
No specific accessibility requirement has been established yet; follow general web-accessibility best practice (keyboard operability, sufficient color contrast, respect for `prefers-reduced-motion` given the pop-up animations) without a confirmed standard to target.
